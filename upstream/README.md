# LiteLLM Python port

The Go port follows the public Python implementation in LiteLLM. The initial reference is `v1.85.0` at the commit in [litellm.ref](litellm.ref), which also matches the revision of Minato's existing LiteLLM image. This is the source baseline for the port. Compatibility is verified by behavior and recorded per area. [LiteLLM v1.85.0](https://github.com/BerriAI/litellm/tree/v1.85.0)

The upstream MIT license notice is included with this port. LiteLLM's `enterprise/` directory has separate terms for use and distribution. [MIT notice](LICENSE.litellm) · [LiteLLM Enterprise license](https://github.com/BerriAI/litellm/blob/v1.85.0/enterprise/LICENSE.md)

## Verify protocol behavior

Full proxy parity remains open. Cross-proxy HTTP checks cover model discovery and selected chat paths. Provider fixtures and Go regression tests cover the additional operations in the table. The route inventory also includes management, policy, and integration surfaces that still need implementations and behavior checks.

With both proxies configured for the same synthetic OpenAI endpoint, LiteLLM `v1.85.0` and the Go proxy returned matching model IDs, object types, creation timestamps and providers for `/models`, `/v1/models` and the corresponding model-detail routes. Assistant content and total token counts also matched for versioned, unversioned and Azure-style chat completion paths.

The same proxy comparison matched both liveness aliases, public readiness without a database, and healthy and unhealthy counts for a targeted Chat Completions deployment.

The full JSON responses from `/public/endpoints` and `/public/agents/fields` match LiteLLM `v1.85.0`. The blog endpoint matched against a local RSS fixture and both proxies returned their cached feed after the fixture stopped. The Go proxy caches failed feed lookups for one minute to bound repeated remote requests.

Both model hub responses matched LiteLLM `v1.85.0` for a public OpenAI chat deployment, a duplicate group, an unresolved group and a configured link. Provider-specific parameter metadata beyond the GPT chat path remains partial.

The public model hub links update matched the Python response. The Go regression test verifies that clearing the configured model list and replacing useful links survive model mutations and a process restart. Go persists these changes in its configured state store and supports in-memory updates without one. LiteLLM gates group updates on database-backed model storage.

An isolated PostgreSQL marketplace fixture verifies registration, repeat registration, public visibility, disabling, lookup and deletion. Go validates repository names and HTTPS plugin URLs and exposes only enabled plugins publicly.

Existing database-backed LiteLLM file identifiers can resolve to an authorized OpenAI or Azure deployment for metadata and content reads, batch inputs and fine-tuning file references. Go reads the existing mapping table and verifies ownership before resolution. LiteLLM batch IDs that embed a model ID resolve to that configured deployment.

PostgreSQL and Go HTTP fixtures cover legacy vector store mappings, user and team ownership, model scopes, retained IDs on retrieval, and file-search routing to the mapped Responses deployment. Go uses the stored provider mapping for the exact legacy ID and requires the request to resolve to a single authorized deployment.

An isolated PostgreSQL fixture verifies reads of existing LiteLLM memory rows, scoped writes, prefix listing, scalar metadata, duplicate detection and deletion.

Go audio fixtures cover the ElevenLabs and Deepgram request transformations, Azure SSML escaping and output formats, and Vertex OAuth headers and binary audio decoding.

A local A2A fixture verifies public card rewriting, private agent visibility, credential handling and streamed relay. Go tests also exercise managed agent creation, publication, rename and deletion across restarts.

A local interactive MCP OAuth fixture covers standard and legacy protected-resource discovery, authorization-server metadata, static and upstream client registration, provider redirect, callback state, client redirect preservation, token exchange, caller binding and code replay rejection. The flow uses the configured callback URL or the origin from PROXY_BASE_URL, and requires a proxy key with access to the MCP server and S256 PKCE, and uses process-local pending state. With PostgreSQL, successful exchanges from keys tied to a user are stored in the LiteLLM user credential table. Scoped MCP requests reuse a current stored token when callers provide no upstream authorization. For configured OAuth clients, concurrent requests on one instance share one refresh of an expired token. A PostgreSQL fixture covers encryption, user isolation and preservation of existing BYOK credentials. [Upstream MCP OAuth endpoints](https://github.com/BerriAI/litellm/blob/v1.85.0/litellm/proxy/_experimental/mcp_server/discoverable_endpoints.py)

A local MCP OAuth fixture verifies form-based client credentials, token reuse, token refresh after upstream rejection, and client-secret redaction from management responses.

Go tests verify Streamable HTTP session initialization, path and key isolation, reuse of one upstream HTTP session across tool calls, and termination with DELETE. Clients can continue using stateless requests. Session and upstream connection state are process-local.

The MCP hub response matched LiteLLM `v1.85.0` with one explicitly public and one private configured server. The Go fixture checks persistence and removal of URL query strings from public entries. Go requires an explicit public flag or listing for discovery. LiteLLM defaults configured servers to public.

Fireworks AI, hosted vLLM, Infinity and DeepInfra rerank fixtures matched the full response from LiteLLM `v1.85.0`, including results and token metadata. Together AI rerank passed the Go provider fixture and accepts a configured base URL. The Go adapters currently drop hosted vLLM and Together AI's unsupported `max_chunks_per_doc` parameter. LiteLLM rejects it.

## Review an upstream release

```bash
git clone --no-checkout https://github.com/BerriAI/litellm.git ../litellm-upstream
git -C ../litellm-upstream fetch --tags origin
bash tools/litellm-diff.sh ../litellm-upstream v1.85.1
python tools/litellm-inventory.py ../litellm-upstream
python tools/sync-litellm-providers.py ../litellm-upstream --check
python tools/verify-litellm-formats.py ../litellm-upstream
python tools/verify-litellm-formats.py ../litellm-upstream v1.85.1
go test ./...
```

Run the script from the Go repository. It lists changed Python implementation paths, tests and shared metadata between the pinned commit and the selected tag. Use `git diff <baseline> <target> -- <path>` in the LiteLLM checkout to examine individual changes.

The inventory command reads HTTP route decorators and provider package directories from the selected Git revision. It finds 696 declared method and path pairs and 119 provider or shared package directories at `v1.85.0`. Route declarations are source anchors for parity work. Feature activation, router prefixes and provider capabilities require separate checks.

For each behavior change, record its upstream commit and Python source path, translate the relevant upstream test or run both implementations against the same simulated provider, then apply the Go change. Advance the pinned reference after reviewing the release and recording any remaining parity gaps. Keep the LiteLLM checkout and its test dependencies in the development environment so the Go deployment stays a standalone binary.

## Container memory comparison

On Docker Desktop, LiteLLM Proxy `v1.85.0` and the Go runtime started with the same YAML configuration and handled a warm-up request plus 60 sequential Chat Completions requests each. Both targeted the same synthetic upstream and returned 12 tokens per measured request. Docker reported 989.9 MiB for the Python container and 6.875 MiB for the Go container after the requests. This comparison covers one non-streaming route and measures container memory after the requests.

The same synthetic Chat Completions workload on Go revision `b211ea4` reported 8.188 MiB for Go and 985.2 MiB for Python after 60 measured requests per proxy. PostgreSQL, callback delivery, tokenization and persistent WebSocket sessions were outside this measurement.
