# LiteLLM Python port

The Go port follows the public Python implementation in LiteLLM. The initial reference is `v1.85.0` at the commit in [litellm.ref](litellm.ref), which also matches the revision of Minato's existing LiteLLM image. This is the source baseline for the port. Compatibility is verified by behavior and recorded per area. [LiteLLM v1.85.0](https://github.com/BerriAI/litellm/tree/v1.85.0)

The upstream MIT license notice is included with this port. LiteLLM's `enterprise/` directory has separate terms for use and distribution. [MIT notice](LICENSE.litellm) · [LiteLLM Enterprise license](https://github.com/BerriAI/litellm/blob/v1.85.0/enterprise/LICENSE.md)

## Verify protocol behavior

Full proxy parity remains open. Cross-proxy HTTP checks cover model discovery and selected chat paths. Provider fixtures and Go regression tests cover the additional operations in the table. The route inventory also includes management, policy, and integration surfaces that still need implementations and behavior checks.

With both proxies configured for the same synthetic OpenAI endpoint, LiteLLM `v1.85.0` and the Go proxy returned matching model IDs, object types, creation timestamps and providers for `/models`, `/v1/models` and the corresponding model-detail routes. Assistant content and total token counts also matched for versioned, unversioned and Azure-style chat completion paths.

The same proxy comparison matched both liveness aliases, public readiness without a database, and healthy and unhealthy counts for a targeted Chat Completions deployment.

The full JSON responses from `/public/endpoints` and `/public/agents/fields` match LiteLLM `v1.85.0`. The blog endpoint matched against a local RSS fixture and both proxies returned their cached feed after the fixture stopped. The Go proxy caches failed feed lookups for one minute to bound repeated remote requests.

Both model hub responses matched LiteLLM `v1.85.0` for a public OpenAI chat deployment, a duplicate group, an unresolved group and a configured link. Provider-specific parameter metadata beyond the GPT chat path remains partial.

The public model hub links update matched the Python response. The Go regression test verifies that clearing the configured model list and replacing useful links survive model mutations and a process restart. Go persists these changes in its configured state store and supports in-memory updates without one. LiteLLM gates group updates on database-backed model storage.

The MCP hub response matched LiteLLM `v1.85.0` with one explicitly public and one private configured server. The Go fixture checks persistence and removal of URL query strings from public entries. Go requires an explicit public flag or listing for discovery. LiteLLM defaults configured servers to public.

Fireworks AI, hosted vLLM, Infinity and DeepInfra rerank fixtures matched the full response from LiteLLM `v1.85.0`, including results and token metadata. Together AI rerank passed the Go provider fixture and accepts a configured base URL. The Go adapters currently drop hosted vLLM and Together AI's unsupported `max_chunks_per_doc` parameter. LiteLLM rejects it.

NVIDIA NIM fixtures matched the full response from LiteLLM `v1.85.0` for both retrieval reranking and `/v1/ranking`. The fixtures covered the provider model name, reconstructed documents and token metadata.

Azure AI's Cohere v2 fixture matched the full response from LiteLLM `v1.85.0`. Azure AI deployment metadata used for base-model spend attribution remains open.

Hugging Face's document-return fixture matched the transformed request, ranking result and token estimates. Each proxy generated its own response ID. The Go estimate counts the upstream JSON with an embedded tokenizer. LiteLLM counts the Python representation and can use model-specific tokenizers.

The watsonx fixture matched the full LiteLLM response using a local IBM IAM token exchange and a configured project. The Go fixture also checks token reuse across requests.

The container fixture matched object, name, creation time and status across LiteLLM `v1.85.0` and Go creation and retrieval. Go tests verify cross-project access checks, list filtering, file affinity and binary streaming. PostgreSQL tests verify that ownership survives reopening the store and that recording a container again cannot replace a different owner.

The Mistral OCR JSON fixture matched the full LiteLLM `v1.85.0` response. Go tests cover multipart upload conversion, original file format detection and rejection of JSON file references.

The Azure AI Mistral data-URI fixture also matched the Python response. Go fixtures cover Vertex Mistral routing and multipart uploads. The Go document downloader rejects private, loopback and other reserved network destinations.

Azure Document Intelligence matched the Python fixture through a 202 response and same-origin polling, including page selection, text and pixel dimensions. Go fixtures cover Vertex DeepSeek's chat request and Markdown response.

Go Bedrock embedding fixtures cover Cohere batching and billed tokens, and Titan multimodal requests with text, image data URLs, output dimensions and image counts. Cohere currently returns one vector type per input.

Go Nova fixtures cover synchronous inference and single-input segmented job submission to S3. Go returns the invocation ARN in `X-LiteLLM-Invocation-ARN` for callers to track the job.

The Go Marengo fixture covers inline image encoding, response normalization and token estimation.

Both UI discovery aliases matched the Python defaults. The eval creation fixture matched object, timestamp, name, criteria and data source. Go fixtures also verify run cancellation, file ID and cursor translation, and model-scope enforcement.

The Go polling fixture checks the queued response, an intermediate text delta, final usage, owner isolation and deletion while using the normal inference stream processing.

The Python Redis fixture and the Go process-local and Redis fixtures each returned a queued polling ID, then a completed response with the same token count. The Redis test retrieved Go's result through a second Go instance. Go enables shared Redis polling via `litellm_settings.responses.background_mode.redis_url` and uses its own Redis key namespace.

The local Chat Completions fixture matched LiteLLM `v1.85.0` for cache-hit usage, hit-only cache key headers and a JSON `cache` object that bypassed reads and writes. Go also honors HTTP `Cache-Control: no-cache, no-store`. Python continued to return a cache hit for that header in the fixture. Two Go instances shared Redis results, and cache administration verified deletion, namespace-scoped invalidation and the preservation of unrelated Redis keys. Go regression tests cover reuse of complete chat SSE streams, upstream retries after incomplete streams, usage during replay and file-content-based caching for multipart transcription. PostgreSQL tests cover historical cache activity. Go uses cache keys scoped to the proxy credential and deployment, with a one-hour TTL by default.

The Google AI Studio Veo fixture matched LiteLLM `v1.85.0` for create request duration and aspect ratio, the processing state and reported duration and resolution. Go fixtures cover polling and retrieval with a same-origin download on Google AI Studio and inline video data on Vertex AI. Status retrieval also accepts LiteLLM video IDs when their provider and model resolve to one configured deployment.

The Google AI Studio Imagen fixture matched LiteLLM `v1.85.0` for sample count, aspect ratio and returned image bytes. Go tests cover Gemini and Imagen on both Google AI Studio and Vertex AI, Gemini multipart edits and Vertex Imagen masks.

The Gemini file upload fixture matched LiteLLM `v1.85.0` for object, status, byte count and creation time. Go tests also cover retrieval, deletion and rejection of an upload session outside the configured provider origin. The Python fixture returned a validation error when retrieving the uploaded file through its URI.

The Gemini File Search fixture matched LiteLLM `v1.85.0` for the vector store name, creation time and status, and for the search query and retrieved snippet. Go tests also check citation deduplication and deployment affinity.

The Gemini Interactions create fixture matched LiteLLM `v1.85.0` for object, model alias, status, output text and token usage. Go fixtures cover agent streaming, previous-interaction routing, scoped access, retrieval, cancellation and deletion. Go adds deployment affinity to returned interaction IDs.

The configured pass-through test matched assistant content and token usage from a synthetic upstream on both proxies. Go coverage also verifies that configured upstream credentials take precedence and that proxy credentials stay on the proxy even when client header forwarding is enabled.

With thirteen synthetic search providers, LiteLLM `v1.85.0` and the Go proxy matched tool discovery on both aliases and normalized results on seventeen search requests, including fallback after an upstream 503. The upstream fixture checked the transformed request and applicable provider credential. The Python SearchAPI.io and Google PSE adapters required environment credentials in the comparison. The Go adapters resolve credentials from tool configuration first and fall back to the environment. A Go regression test verifies that key and team scopes intersect and denied requests never contact the search provider.

The Go and Python checks share eight cases for structured output in both directions. They cover explicit JSON Schema, schema defaults, JSON object mode and plain text. ## Review an upstream release

```bash
git clone --no-checkout https://github.com/BerriAI/litellm.git ../litellm-upstream
git -C ../litellm-upstream fetch --tags origin
bash tools/litellm-diff.sh ../litellm-upstream v1.85.1
python tools/litellm-inventory.py ../litellm-upstream
python tools/sync-litellm-providers.py ../litellm-upstream --check
python tools/verify-litellm-formats.py ../litellm-upstream
python tools/verify-litellm-formats.py ../litellm-upstream v1.85.1
go test ./...
```

Run the script from the Go repository. It lists changed Python implementation paths, tests and shared metadata between the pinned commit and the selected tag. Use `git diff <baseline> <target> -- <path>` in the LiteLLM checkout to examine individual changes.

The inventory command reads HTTP route decorators and provider package directories from the selected Git revision. It finds 696 declared method and path pairs and 119 provider or shared package directories at `v1.85.0`. Route declarations are source anchors for parity work. Feature activation, router prefixes and provider capabilities require separate checks.

For each behavior change, record its upstream commit and Python source path, translate the relevant upstream test or run both implementations against the same simulated provider, then apply the Go change. Advance the pinned reference after reviewing the release and recording any remaining parity gaps. Keep the LiteLLM checkout and its test dependencies in the development environment so the Go deployment stays a standalone binary.

## Container memory comparison

On Docker Desktop, LiteLLM Proxy `v1.85.0` and the Go runtime started with the same YAML configuration and handled a warm-up request plus 60 sequential Chat Completions requests each. Both targeted the same synthetic upstream and returned 12 tokens per measured request. Docker reported 989.9 MiB for the Python container and 6.875 MiB for the Go container after the requests. This comparison covers one non-streaming route and measures container memory after the requests.

The same synthetic Chat Completions workload on Go revision `b211ea4` reported 8.188 MiB for Go and 985.2 MiB for Python after 60 measured requests per proxy. PostgreSQL, callback delivery, tokenization and persistent WebSocket sessions were outside this measurement.
